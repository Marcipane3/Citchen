01Summary

The short version, for reading on a phone.

Verdict

The code does not need a V3. v2 is healthy: 206 automated tests, four languages, offline-first, Google Drive sync, and a shared shopping list. A rebuild for its own sake would cost three to five months and mostly move working code around.

A V3 makes sense when something outside the code changes: who the app is for, where people get it, or who pays for the AI. So the first V3 task is a decision, not a build.

Five things to know

  1. Audience decides the size. "Me and my partner" is a few v2.x releases. "Friends and family" is a solid V3 of about three to four months. "Public product" is a small business with legal, support and payment duties, roughly three to five times the work.
  2. The Play Store is reachable without a rewrite. Google supports wrapping a PWA as a Trusted Web Activity. It needs a custom domain, a Lighthouse score of at least 80 and a working offline start.
  3. The iPhone App Store is the expensive part. Apple rejects "repackaged websites" (guideline 4.2). iPhone users can keep using the home-screen PWA.
  4. AI is cheap per person, but not free to share. About $0.65 per active user per month, $2.35 for heavy use. Paying for other people's AI needs a small server (a proxy), because a shared key can never ship inside the app.
  5. The real technical debts are two: recipes and the shopping list sync through two separate engines, and there are no end-to-end browser tests. Both can be fixed now, in v2.x, which makes any V3 safer.
Recommendation

Plan "V3 Personal Pro": friends and family, a PWA plus an Android Play build on your own domain, data stays in each user's Google Drive, everyone brings their own AI key, default food photos for the base recipes, one sync engine and an end-to-end test suite. Keep "V3 Product" (accounts, payments) behind a measured gate. Start with the foundation work in v2.x during Q4 2026, and decide the V3 intent in December.

What works well

  • Offline-first. The app opens from the phone's storage first, then syncs. A missing network never blocks cooking.
  • Your data in your Drive. Recipes live in one rezepte.json file in your Google Drive, with the narrow drive.file permission. No server holds anyone's data.
  • A stable data contract. The recipe file follows SCHEMA.md, which v1 and the Claude project instance also use. Translations are display-only, so the stored data stays German and consistent.
  • Honest AI. AI features use the user's own Anthropic key (BYOK). Without a key or network the app says why, instead of failing silently.
  • Quality habits. Every release bumps the build and cache stamps. Tests guard translations, the offline file list, syntax, sync merges and the German-data rule. A QA agent fleet reviews architecture, bugs, data integrity, UX and releases.

03How a major version works

A stage-gate process, the same logic as a capital project: short phases, each closed by a gate with evidence.

A feature release adds to a structure that stays. A major version may change the structure itself: platform, data model, distribution, business model. That freedom is what makes it risky. The typical failure is not bad code. It is rebuilding everything without a clear reason and carrying the old problems into the new structure.

The counter-measure is to spend little until the evidence is in. The first four phases are mostly thinking and small throwaway prototypes. The build only starts when the decisions are written down and the risky assumptions are tested.

Ways of working during the build

  • Parallel run. V3 grows next to v2, as v2 grew next to v1. Nobody switches until gate G6.
  • Vertical slices. Each slice goes end to end (screen, data, test, translations, docs) and could ship on its own.
  • Definition of Done per slice: tests green, all four languages, dark and light checked, phone width checked, changelog line, roadmap updated.
  • One decision log. Every structural choice becomes an ADR. Changing course means a new ADR, not a quiet drift.
  • Weekly phone demo. Ten minutes with the real build in hand catches what tests miss.

04The seven decisions

Highlighted options are the recommendation for "V3 Personal Pro". Each becomes an ADR once you decide.

D1

Purpose and audience

1aPersonal. You and your partner. v2.x releases already cover almost everything.
1bFriends and family, up to ~100. Strangers to the code install it with their own Google account. Needs onboarding, a privacy policy and the Google sign-in app out of test mode.
1cPublic product. Store listing, accounts, support, possibly payments. An ongoing operation.

Move from 1b to 1c only after a validation gate, for example ten weekly active users who are not you, four weeks in a row.

D2

Distribution

2aPWA only (today). Works on Android and iPhone via "Add to Home Screen". Found only by link.
2bPWA plus an Android Play build (TWA). Same code, wrapped with Bubblewrap. Needs Digital Asset Links at the domain root, Lighthouse 80+, offline start returning HTTP 200.
2cPlus iPhone App Store (Capacitor). Apple's guideline 4.2 rejects thin web wrappers, so it needs real native features. Yearly Apple fee.

On a project-pages address like marcipane3.github.io/Citchen/ the domain root belongs to a different repository, so a custom domain is the clean route for 2b.

D3

Stack and code base

3aPlain ES modules, no build (today). Hand-editable, zero dependencies, fast.
3bPlain modules plus one small build script that generates the offline file list and versioned asset names. Keeps 3a's strengths, removes its one chore.
3cLight framework (Svelte or Preact with Vite). Components and an ecosystem, but a rewrite of 47 modules and a larger dependency surface.
3dNative apps (Kotlin, Swift). Two code bases, nothing reused.

Keeping third-party scripts at zero is also a security control: the AI key lives in browser storage, and any added script could read it.

D4

Data and sync

4aEach user's own Google Drive (today), plus one shared sync engine with a merge rule per file type.
4bBackend database (Supabase or Firebase). Easier accounts and sharing, but you become the GDPR data controller, pay for hosting, and the Claude project can no longer edit the recipe file directly.
4cHybrid. Drive for data, a tiny server only for what Drive cannot do (public share links, AI proxy).

4a is the app's privacy promise and costs nothing. 4c is the natural next step if D5 ever needs a proxy.

D5

AI and money

5aBring your own key (today), with all model calls kept behind one client module so a proxy can be added later.
5bSponsored quota. You pay for friends and family up to a cap. Needs a proxy with per-user limits.
5cPaid tier. Subscription covers AI. Needs proxy, entitlement checks and store billing or a web checkout link.

BYOK is the right default for a technical circle. For non-technical friends it is the biggest friction point, so 5b is the likely second step.

D6

Content

6aDefault food photos for the 105 base recipes: AI-generated in one consistent style, WebP up to ~80 KB each (about 8 MB total), loaded on demand rather than pre-cached.
6bCalories and macros from a bundled USDA/Frida table with an AI fallback (roadmap Epic L).
6c"Gesund & Langlebig" knowledge section (Epic N). Better after nutrition data exists.
D7

Domain and old versions

7aCustom domain for V3 (about €10–15 a year), independent of the GitHub username.
7bRetire v1 with a redirect; keep v2 reachable read-only for 30 days after launch.
7cStay on the GitHub address and run V3 at /v3. Cheapest, but blocks a clean Play build.

Two cheap savings exist today. Caching the assistant's system prompt (it repeats the full recipe list on every call) cuts the suggestion cost by roughly half. Moving capture from claude-sonnet-4-6 to claude-sonnet-5-5 cuts capture cost by about a third.

If V3 ever charges money (Path B)

From 30 June 2026, Google Play charges a 10% service fee on auto-renewing subscriptions in the US, EEA and UK, plus a 5% billing fee when Play Billing processes the payment. Developers may also link out to their own web checkout under Google's billing-choice programme. At a €2.99 monthly subscription, about €2.54 remains after Play fees. A typical user's AI costs about €0.60, so roughly €1.90 per paying user is left before support time and taxes. A heavy user nearly cancels that out, which is why any paid tier needs usage caps.

Read this as

Money is not a reason to build V3. At family scale the whole app costs under €20 a year to run. Payments only make sense if D1 becomes "public product", and then they are an operational commitment, not a feature.

08Data and migration

What moves, what does not, and the one trap with a new domain.

The domain trap

Browser storage belongs to an origin (scheme plus host), not to a folder. Today v1, v2 and any /v3 folder all share marcipane3.github.io, so they see each other's storage. That is convenient for migration and dangerous for collisions. A custom domain is a new origin: Drive data is unaffected, but everything stored only in the browser starts empty. The fix is a small "move to the new app" helper in v2 that exports local settings, plus a check that nothing is waiting to sync.

Rehearsal before beta (gate G5)

  1. Copy the real rezepte.json and einkaufsliste.json.
  2. Run V3 against the copies in a clean browser profile.
  3. Compare every recipe after a round trip: id, name, ingredient count, photo references.
  4. Run v2's test fixtures through V3's loaders.
  5. Only then point V3 at the real files.

Rollback

Because the file format stays the same, v2 can read anything V3 writes. Keep v2 reachable for 30 days after launch. In the Play console, a bad release can be halted and the previous one kept. Feature flags switch off risky features without a new build.

AGlossary and sources

PWA
Progressive Web App. A website that installs to the home screen and works offline.
TWA
Trusted Web Activity. Google's way to publish a PWA in the Play Store without rewriting it.
Digital Asset Links
A small file on the website (assetlinks.json) that proves the app and the site belong together.
BYOK
Bring your own key. Each user pastes their own Anthropic API key; the app never holds a shared one.
Proxy
A small server that holds a secret key and forwards AI calls, with limits per user.
ADR
Architecture Decision Record. One page: context, options, decision, consequences.
Stage-gate
Work in phases; each ends with a go/no-go decision based on evidence.
Origin
Scheme plus host of a web address. Browser storage is kept per origin.
LWW
Last writer wins. On conflict, the newer version replaces the older one.
Item merge
Conflicts resolved per list item, so two people can edit the same list at once.
